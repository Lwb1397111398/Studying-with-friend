- [2 证据出处] 核心实证数据matchB_dyn.json(401条逐页原始)不入库，仅聚合统计值内联入库（Phase 0报告§5）。虽已声明双轨引用，但若Phase 0报告§5聚合值本身出错，逐页原始无法回溯校验 → 建议：将matchB_dyn.json的401条逐页数据（page/median/gate/secs）以JSONL格式入库至docs/plans/data/或类似路径，与Phase 0报告§5聚合统计互相校验；.e2e/运行时产物不入库的纪律不受影响（入库的是静态快照非动态生成物）
- [4 验证闭环] V5核对命令(git diff grep)的输出判定规则为「出现-前缀删除上述符号行即违规」，但REC_BATCH/OcrCtc.decode/text.isNotEmpty在新增上下文中可能以+前缀出现多次，期望输出描述「仅+前缀同款行」需人工逐行判断同款，非零上下文工程师可能误判 → 建议：将V5命令改为更精确的awk/grep组合：如git diff 2056de0 -- ... | awk '/^[-+].*(REC_BATCH|OcrCtc\.decode|text\.isNotEmpty)/{print $0; n++} END{exit (n>0 && $1~/^-/) ? 1 : 0}'，使违规判断由退出码自动化；或在期望输出中给出精确的期望行文本（含前缀符号）作为diff基准
- [3 方法可行] §8 Bitmap路径JVM不可测的处置方案明确但偏被动：不引Robolectric(依赖变更须老板确认)、不做接口抽象(超范围)、运行时验证归小计划B。这意味着recognize段核心的裁剪/缩放/像素提取逻辑在本包完全无JVM侧验证，仅靠数学纯函数(OcrRecPre)单测覆盖口径，而Bitmap操作正确性(如坐标系、recycle时序、跨批次复用)无自动化守卫 → 建议：① 在§8增补一条「若小计划B E2E发现Bitmap路径问题，本包需回改」的回查触发条件与判据；② 考虑是否可在不引入新依赖的前提下用Robolectric的已有shadow Bitmap做最小化验证（检查P6b是否已引入Robolectric作为测试依赖），若未引入则保留现状但加一条「B阶段若Bitmap路径出错，本包V2需追加instrumented测试」的前置声明
