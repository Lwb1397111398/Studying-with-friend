## 0. 结论先行

**判据实测：①②③c 过，③③b 阻塞记档，④ 不过（No-Go 倾向）。** 总体判定=**No-Go 倾向，不自动回退，按决策案 §9 条款报老板拍板（两选项见 §7）**。

- 功能本身全链路可用：shpc 461 页扫描书两轮完整导入出书（4 章 1293 段落库，两轮结果逐位一致），E2E 实录抓出的 4 个代码 bug 全部修复并回归通过（commits b2a29ac/935a790/b92db18）。
- 不过的核心不是代码缺陷，是**判据标定源错位**：判据体系（置信度 0.85 阈值、兜底 6-20 页、≤16min）全部建立在 P6a PoC 数据上，而 P6a PoC 用的是 PC 侧 rapidocr 原型；生产引擎是 PP-OCRv5 mobile ONNX——**不同模型，置信度口径不同**。实测生产引擎对 shpc 461 页中 396 页页均置信度 <0.85（P6a 预测 ≈0 页触发），连带仿真书 22 页中 15 页兜底、章标题召回 0/8。兜底是引擎对识别没把握的页交视觉转写的**正确保守行为**（人工抽读兜底页 OCR 草稿确认质量确实差），管线各环节行为与设计完全一致。
- 真机联测**不能翻案兜底页数**（同模型同置信度输出，与 CPU 无关），只能复核**耗时**（模拟器 x86 推理 2.0-2.8s/页 vs P6a 口径 1.24s/页，真机 ARM 预计显著快于模拟器）。

## 2. 根因定性：F9 置信度口径错位（本阶段最重要的发现）

**取证链（全部 MEASURED，S7-2 两轮 + 快照取证）：**

1. ocr_verify 快照 p378 行级置信度两极分化（0.49-0.99，median 0.895），大量行贴 0.5-0.7 区间——页均被拉下 0.85 线。
2. 兜底页 OCR 草稿人工（AI 目视）抽读质量确实差：繁体混入（「损害賠償」）、p308 整页不可读——**置信度低是引擎的真实自我评估，兜底是正确保守行为**。
3. 反证排除「整体失灵」：p001 封面大字识别极好（置信度高）；p381 画质良好正文页也被兜底——排除「画质差才兜底」的简单归因，是模型对该书域的系统性低置信。
4. 两轮导入 fallbacks 逐位一致（LOW_CONF=396/DIAGRAM=5、fragmentLinesMerged=1）——管线确定性成立，非随机扰动。
5. 口径溯源：P6a PoC 50 页数据（median 0.9751、<0.85 页数 0）产自 PC 侧 rapidocr 原型；生产引擎为 PP-OCRv5 mobile ONNX 三件套（det+rec+dict 21MB）。**F9 的全部判据输入（85% 阈值几乎不触发、兜底 6-20 页、461×1.24×1.5≤16min）无法外推到生产引擎。**

**根因定性：不是实现 bug，是计划案前置事实 F9 的标定源（rapidocr）与生产模型（PP-OCRv5 mobile）置信度口径系统性错位。** 0.85 阈值对 rapidocr 是宽松线，对 PP-OCRv5 mobile 是收紧线（该模型置信度天然两极分化）。

## 4. S7 E2E 实录：抓出的实录问题与修复（JVM 单测测不出、只有真机/E2E 才暴露）

1. **ocrMode 数字书误伤**（b2a29ac）：数字书被当作 OCR 模式→插图全丢+图页不排除出视觉队列（mfzz 146→150、figures 4→0）。修复=ocrMode 仅扫描书置位；回归三重一致。
2. **UNICODE_CHARACTER_CLASS 平台崩溃**（935a790）：Android regex 引擎不支持该 flag，OcrTextPostProcessor 全量 Pattern 预编译即崩（JVM 单测全绿、Android 一跑就崩——分层测试价值的直接实证）。修复=显式字符类 WS/DIGIT/CIRCLED；替换中丢量词（`\s*`→`(?:$WS)*`）被 Y 判据 fixture 回放 p003 行 5 抓住，新增全角空格/全角数字单测锁定。
3. **OCR 进度假卡死**：提取段满格 progress 残留使 ImportScreen 的 `p != null` 分支盖掉 phase 文案，OCR 全程显示「提取 PDF 461/461 页」假象。修复=runOcrPath 开头 `progress = null`；实测进度「本地文字识别 第 258/461 页（约剩 4 分钟）」实时刷新。
4. **OCR 零日志**：判据④分离计时无可观测。修复=tag "OcrImport" 四条日志（vertical prefilter/full scan、Pass1 done render/infer/post 分项、Pass2 done fallbacks/byReason/fragmentLinesMerged/pass2Ms）——本报告 §3 全部数据即产自该日志。
5. **生产引擎置信度口径错位**（非代码 bug，判据级发现，见 §2）——LOW_CONF 396 页证伪 F9「低置信触发≈0」预测。

## 7. 老板拍板项：判据④ No-Go 倾向的处置（决策案 §9 条款，不自动回滚）

**人话背景**：扫描书导入功能已经能用了（模拟器实测），但「判据④」两条硬指标没达标——总耗时略超（16.6 vs 16 分钟，模拟器慢，真机可能没问题），**兜底页数远超上限（401 vs 70 页，这个真机也救不回来）**。根因是当初定判据用的测试模型（PC 原型）和真机上的小模型（PP-OCRv5 mobile）对同一页面的「自信程度」打分差很多：小模型更「谦虚」，大量页它自己承认没把握，按设计交给了视觉转写兜底。功能没有坏——有视觉配置的用户，这些页会被 AI 转写补齐（效果好但调用多）；没配置的用户会看到如实提示（401 页未能识别，可配置视觉增强补齐），但书的很大部分是空的。

| 选项 | 内容 | 代价 |
| --- | --- | --- |
| **A 保留功能，开关默认开（推荐）** | 扫描书可用；质量备注四件套如实提示；配合 §6-1 真机联测复核置信度分布后，若确认 0.85 阈值对该模型过严，再立项重标定（须老板点头改标定初值，不属放宽既有判据） | 无视觉配置的用户导入低质量扫描书会得到部分空白的书（有明确提示）；兜底页视觉调用成本高（与纯视觉路径同量级） |
| B 严格按 No-Go 执行回退 | `ocrEnabled` 默认改 false 热修发布，扫描书回到现状（导入拒绝） | 扫描书重新不可用（回滚成本，§9 原文）；已完成的 E2E 闭环与 5 项实录修复保留在代码里 |
| C 折中：开关默认开+导入前预警 | A 的基础上，设置页 OCR 开关旁加「当前模型对部分扫描件置信度偏低，建议配合视觉增强使用」说明 | 多一处文案，无行为变化 |

决策前不向其他设备变更默认行为（§9 原文）。A 与 C 的差别仅在提示文案，默认推荐 A（C 的文案可在真机联测出数据后一并定）。
